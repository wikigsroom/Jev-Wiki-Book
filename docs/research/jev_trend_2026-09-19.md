# JEV 小模型风潮研究稿

更新时间：2026-09-19（Asia/Taipei）

> 历史调研，不是当前软件的实现说明。当前本地系统使用社区 NanoJev 权重，项目与路径统一命名为 JEV；见 [README](../../README.md)。下文 JAV/jav 仅保留为历史搜索词或语言代码。

## 0. 先给结论

本轮近三日公开社区真正集中讨论的对象是 `Jev`，不是 `JAV`。你给出的 Sprite Fusion 链接也明确讨论的是 Jev。英文精确搜索 `JAV small model` 后，主要结果落在 Hugging Face 的 `jav` 语言过滤器，`jav` 是 Javanese（爪哇语）的语言代码；这条结果线没有形成 2026-09-16 至 2026-09-19 的新模型风潮。

因此，本稿将两条线分开：

1. 主线：`Jev`，TypeSafe AI 在 2026-09-14/15 前后推出的 System One 决策模型，以及近三日围绕它爆发的开源复刻和应用。
2. 歧义线：`jav`，Hugging Face 上的爪哇语小模型，以及 Java/JVM 本地小模型工具。这些不是本轮 Jev 风潮的同一对象。

一句话判断：这不是“又一个更小的聊天模型”风潮，而是“把模型从文本生成器改成软件内部的概率决策部件”的风潮。社区正在争夺的核心不是聊天质量，而是低延迟、可约束输出、置信度、批量判断、代理控制和本地复刻。

## 2. Jev 到底是什么

TypeSafe AI 将 Jev 定义为首个 `System One Model`。它接收一份状态和一组预先定义的 typed questions，返回程序可以直接消费的判断结果、概率分布和置信度，而不是自然语言回答。

典型接口可以抽象为：

```text
state + typed questions
        ↓
choice / score / noul + probabilities + confidence
        ↓
application code decides the next action
```

公开接口的三类基本问题是：

- `Choice`：从候选集合中选一个，并返回各候选概率。
- `Score`：在有序等级上评分，并返回分布或期望等级。
- `Noul`：对一个命题给出“是”的概率。

TypeSafe 的技术叙事有三个组成部分：

1. `RLCD`：Reinforcement Learning for Calibrated Decisions，目标是让概率和实际正确率更一致，而不是只优化人类更喜欢的文字答案。
2. 并行采样：多个问题在同一份状态上并行评估，减少逐 token 生成和输出解码。
3. 类型约束：候选集合和输出结构由调用方定义，因此模型不会生成候选集合之外的新字符串或破坏 JSON 结构。

这里必须分清两件事：类型安全不等于语义正确。Jev 可以保证返回值属于规定的类型，却仍然可能选错，或者给错误答案过高的概率。它真正的生产价值取决于校准、阈值、回退路径和业务数据上的实测。

公开资料中最常被引用的产品数字是：端到端约 70 至 500 毫秒、输入价格约 0.042 美元/百万 token、输出 token 不收费。它们是 TypeSafe 的产品或内部 workflow 声明，不是统一外部基准。官方也明确说明，不同网络距离、状态长度、问题设计和并发度会改变结果。

Jev 的参数量、底层架构、训练数据和权重没有公开。它是早期访问的闭源托管 API，因此不能把 Jev 称为“已知参数规模的小模型”。更准确的说法是：它是一个面向小决策的模型产品和接口范式。

## 3. 近三日时间线

### 2026-09-14/15：发布和定位

TypeSafe 从隐身状态发布 Jev，并提出 `System One Models` 这一类别。官方定位非常明确：LLM 为人写字符串，System One 模型为软件做判断。发布材料展示了 Doom、Wikiracing 等演示，并把重点放在“同一状态上一次性提出多个问题”。

这一天的传播核心不是某个公开 checkpoint，而是三个新鲜的产品承诺：

- 把原本需要“生成文本、解析 JSON、修复格式、重试”的判断，直接变成 typed output。
- 用概率和置信度让代码决定自动执行还是人工升级。
- 用极低输入价格和较低延迟，让模型进入 Agent、UI 和游戏循环。

### 2026-09-16：媒体扩散，游戏和 Agent 成为主叙事

媒体开始集中报道 TypeSafe 的融资、创始团队背景和“机器原生智能”定位。公开演示迅速被解读为“AI 可以进入实时软件控制环”。

但 Doom 等演示的关键限制也在这一阶段被指出：输入是结构化或文本化的游戏状态，不是模型直接理解原始画面；动作执行、状态压缩和循环控制仍由外围代码负责。

### 2026-09-17：独立分析和第一批复刻出现

社区开始把问题从“它有多快”转向“它到底新在哪里”：

- 现有小分类器、约束解码和 JSON schema 是否已经足够？
- 对比 LLM 时，是否故意让 LLM 生成长解释，放大了 Jev 的优势？
- 高置信度错误如何处理？
- 并行问题是否真的等价于一个经过专门训练的决策模型？

同日出现多条开源路径：直接读取开放模型 logits、给小模型增加 decision heads、搭建兼容 `POST /v1/systemone` 的服务、把 Jev 放到浏览器 Agent 的动作选择层。

### 2026-09-18/19：从模型讨论转向项目潮

这两天出现了明显的应用层扩散：

- Browser Use 发布 `jev-ultrafast`，用 DOM 元素表而不是截图让 Jev 选择操作和目标。
- Sprite Fusion 发布实时生成平台跳跃关卡的案例，直接把 Jev 放进游戏状态到下一段地形的循环。
- `NanoJev` 给出 0.6B backbone、决策头、训练脚本、游戏回放和概率评估。
- `SemIf`（原 `OpenJev`）把 Qwen3.5-4B、MiniCPM5-2B 等开放模型变成可在本地或浏览器运行的 typed-decision 基线。
- Kotoba Labs 在 Hugging Face 发布 `open-jev-deberta-v3-large`，提供更传统的 encoder + decision head 路线。
- `razorback16/openjev` 用 DiffusionGemma 26B-A4B 和 vLLM 提供兼容服务，同时添加图像、thinking 等扩展。
- GitHub 上出现多个 `awesome-jev` 目录，内容从 SDK、Agent 路由、MCP、数据库扩展扩展到交易、无人机和游戏实验。

这里的“风潮”已经不是单个仓库走红，而是围绕同一个协议同时长出了模型复刻、应用集成、目录索引、评估和批评五类工作。

## 4. 你给的 Sprite Fusion 文章：实际做了什么

文章标题是《Generating levels in real time with the Jev model》，作者 Hugo，发布时间为 2026-09-18。它是本轮最直观的游戏案例之一，但应当被理解为工程演示，不是模型能力的独立基准。

### 输入和任务

作者制作了一个霓虹夜风格的 runner 原型，使用 Sprite Fusion 生成像素美术，用 PhaserJS 搭建游戏，再把当前游戏状态发送给 Jev。示例状态包含：

```json
{"x":158.86,"y":86.87,"vx":2.27,"vy":-2.34,"grounded":false,"dash_ready":true}
```

模型的任务不是生成完整地图，而是决定下一段 terrain slice 的参数。候选空间被限制为：

- 表面类型：solid roof 或 one-way ledge。
- 宽度：2、3 或 5 个 block。
- 前置间隔：0、1 或 2 个 block。
- 高度：第 4 至第 9 行。

一次调用并行提出多个 Choice 问题，再由游戏代码把结果转换为实际方块。文章展示的一次输出包含四个 surface：不同的 ledge/roof、宽度、间隔和高度。

### 实测结果

作者记录了 5 次请求：

- API 延迟：约 319 至 375 毫秒。
- 估算每次成本：约 0.00057 美元。
- 这段演示总成本：约 0.00286 美元。

这是一个重要的现实修正：产品叙事常说“亚秒级”，但游戏案例实际是约三百毫秒级。因此它更适合提前生成、缓冲下一段内容或低频改变规则，不适合未经设计就让每一帧都等待远程 API。60 FPS 的一帧预算约 16.7 毫秒，Jev 不能直接替代本地物理、碰撞或确定性规则。

### 文章真正证明了什么

它证明了：当状态被压缩、动作空间被提前设计、代码负责执行和安全约束时，云端 typed-decision 模型可以以很低的单次成本参与运行时内容生成。

它没有证明：

- Jev 能理解原始画面或原始视频。
- 生成的关卡一定可玩、平衡或比手写规则好。
- 离线运行、断网容错或高并发下仍然稳定。
- 模型能推导出复杂的物理约束。

Reddit 讨论也准确指出了下一步真正有价值的问题：能否把角色物理、可达范围和可调难度作为状态约束，让模型的选择不是“看起来合理”，而是可验证地 playable。

## 5. 开源社区项目谱系

### A. 调用闭源 Jev 的应用层

这些项目不是 Jev 的开源版本，而是把 Jev 当作快速判断层。

| 项目 | 方向 | 关键做法 |
| --- | --- | --- |
| `browser-use/jev-ultrafast` | 浏览器 Agent | DOM 元素表作为状态，Jev 选择操作和目标；只在需要输入文字时调用小型文本模型 |
| `jkudish/jev-browser` | 浏览器/MCP/CLI | 每步提出动作、目标完成、是否卡住等多个问题，并记录置信度、错误、截图和成本 |
| `realZachi/pg-jev` | PostgreSQL | 批量把行转换为 Noul 问题，在一次请求中判断多行，强调缓存和批处理 |
| `awesome-jev` 目录中的 router、MCP、review、guard 项目 | Agent 基础设施 | 用 Jev 做模型路由、工具调用门控、代码审查、停止条件和风险判断 |

这条路线的特点是：它没有缩小模型，而是缩小每次模型调用的职责。Jev 做“下一步是什么”，其他模型负责写文字、代码或填充字段。

### B. 直接做本地复刻

| 项目 | 模型/规模 | 复刻重点 | 现阶段应如何理解 |
| --- | --- | --- | --- |
| `TianyuCodings/NanoJev` | Qwen3-0.6B backbone | decision heads、Choice/Score/Noul、动态候选、批量问题、训练和回放 | 最完整的端到端研究型复刻之一，但不是 TypeSafe 权重或训练的复现 |
| `TheoLeeCJ/SemIf`，原 `OpenJev` | Qwen3.5-4B、MiniCPM5-2B 等 | 直接读取 option logits，不生成 JSON；支持共享状态和浏览器基线 | 重点是测量“直接 typed logits”相对短 JSON 生成的系统收益 |
| `com-kotobalabs/open-jev-deberta-v3-large` | DeBERTa-v3-large encoder | 公开分类数据、cross-entropy + Brier、温度校准、动态问题 | 提供了更传统、可解释的开放权重基线，作者明确声明与 Jev 数字不可直接比较 |
| `razorback16/openjev` | DiffusionGemma 26B-A4B | 兼容 TypeSafe SDK 的 `/v1/systemone` 服务、并行决策和扩展字段 | 更像可部署的兼容服务，规模并不“小”；还不是 TypeSafe Jev |

### C. 汇总和生态索引

多个 `awesome-jev` 仓库在 9 月 17 至 19 日快速更新。其中一个 GitHub 目录声称已经收录 410 个条目，涵盖官方资源、SDK、集成、Agent、浏览器、游戏、评估和研究。这个数字只能作为生态热度信号，不能当作 410 个成熟项目：条目中有文章、目录、实验仓库和重复索引。

## 6. 本轮风潮的五个核心方向

### 6.1 从“回答”转向“控制流”

过去的 Agent 常让大模型输出一段 JSON，再由程序解析、校验、重试。Jev 的核心宣传是直接让模型回答一个有界问题，结果可以进入 `if`、路由表、评分器或策略函数。

这使模型更像一个“带概率的语义 if”，而不是聊天机器人。真正有价值的工作不在于让模型写得更长，而在于把状态、候选项、阈值和回退规则设计好。

### 6.2 “小模型”这个词正在发生语义漂移

本轮至少有四种不同含义被混在了一起：

1. Jev 作为低成本、小决策粒度的托管模型，但真实参数量未知。
2. NanoJev 这类 0.6B 本地决策模型。
3. 2B 至 4B 的开放模型，通过 logits 或 decision head 复刻接口。
4. 26B-A4B 这类大总参数、低 active 参数的 MoE 兼容服务。

所以“Jev 小模型”不是一个精确的模型规格。更精确的研究对象是：`typed decision model`、`System One model`、`parallel classification with calibrated probabilities` 和 `machine-native AI`。

### 6.3 游戏成为最快的示范场

游戏天然具备：短状态、有限动作、连续循环、可测延迟、明确成本和可视化结果。Jev 选择下一段地形、下一步动作或下一项技能，比让它写一段游戏剧情更能展示这种范式。

Sprite Fusion 的案例特别说明了“状态压缩 + 候选设计 + 代码执行”的组合方式：模型并没有直接生成地图文件，而是从宽度、间隔、高度和表面类型中选择，确定性代码随后完成落地。

### 6.4 Browser Agent 是最强的早期应用方向

网页的交互元素本来就是一个离散动作空间：点击哪个按钮、选择哪个下拉项、是否滚动、是否结束。`jev-ultrafast` 将页面转换为带编号的元素表，不依赖截图作为默认输入，让模型可以在操作层快速判断。

这一模式比“让一个大模型看截图并解释页面”更容易测量，也更容易做安全边界：只有被观察到的元素能够进入候选集，执行器还要重新验证页面新鲜度、遮挡和表单状态。

### 6.5 从 API 调用走向蒸馏和本地化

Jev 仍然是闭源 API，但它的接口非常适合被复刻：状态、问题、候选项、概率、置信度。社区因此迅速尝试：

- 直接从开放模型 logits 读取答案。
- 用 Jev 或强模型产生标签，再训练更小模型。
- 用 Brier loss、温度校准和完整分布，而不是只训练 argmax 标签。
- 用真实游戏、浏览器和 Agent 轨迹做闭环评估。

这条路线的长期影响可能比 Jev 本身更大：以后很多系统会把通用 LLM 用作教师或规划器，把小决策模型部署在热路径上。

## 7. 目前最容易被夸大的地方

### 7.1 “不能幻觉”只解决了输出空间问题

Jev 不输出候选集之外的字符串，这解决了格式漂移、字段缺失和无效工具名。但它仍会对错误候选给出高概率。一个错误的 `approve = true` 比一个解析失败的 JSON 更危险，因为它可能静默进入业务流程。

生产系统必须保留：

- 版本化模型 ID。
- 概率和置信度日志。
- 高风险操作的人工复核。
- 分布漂移和高置信度错误监控。
- 与规则、检索、强模型或人工的回退路径。

### 7.2 速度和成本不能脱离基线

TypeSafe 的 193.6 倍速度、444.6 倍成本等数字来自其特定 workflow，对比的是完整生成式模型调用。独立舆情分析收集了用户自报数据，给出的中位数约为 7 倍速度、30 倍成本下降，但它也明确没有重跑实验，且不同作者使用了不同基线、输入长度和计时口径。

公平基线至少应包括：

- 当前实际使用的最短 LLM 调用，而不是要求 LLM 额外写解释。
- 一个训练好的任务专用分类器。
- 规则和约束解码。
- 一个本地小模型的直接 logits 读数。
- 端到端网络、序列化、执行和重试时间，而不是只看模型 forward。

### 7.3 游戏示范不是每帧实时 AI

Sprite Fusion 的 319 至 375 毫秒请求延迟足以生成下一段内容，但不适合替代物理引擎或每帧控制。更合理的架构是：

```text
本地物理/规则循环
        ↓
提前观察并请求下一段内容
        ↓
缓冲生成结果
        ↓
必要时用规则兜底
```

### 7.4 现阶段不是多模态模型

公开资料显示，Jev 首发阶段主要接收文本、JSON 对象或文本列表，不接收图片、音频和视频。Doom、驾驶和游戏演示依靠外围代码把环境变成结构化状态。因此不要把本轮风潮误读成“视觉模型已经进入毫秒级实时控制”。

### 7.5 它并不自动胜过普通分类器

当任务稳定、标签固定、训练数据充足时，专用分类器通常更便宜、更稳定、更容易离线部署。Jev 的优势更可能出现在：问题需要快速改变、候选项运行时定义、需要多个判断共享状态、还没有足够标注数据的阶段。

## 8. 对“JAV”精确搜索的结果

如果你说的确实是小写 `jav`，当前公开结果主要有三类：

### 8.1 `jav` 作为爪哇语语言代码

Hugging Face 的语言筛选 `language=jav` 返回爪哇语模型，包括 `goldfish-models/jav_latn_5mb`、`jav_latn_10mb`、`jav_latn_100mb`、`jav_latn_full`、一些多语种模型和 `BabyLM-community/jav-baseline-small`。这些项目的更新时间主要在 2024 至 2025 年，不构成 2026-09-16 至 2026-09-19 的集中热点。

### 8.2 Java/JVM 上运行小模型

另一个相近方向是 Java 原生推理。`integrallis/models` 近期维护了 Java 25 的 GGUF 推理、Vector API、Qwen、Gemma、SmolLM 等支持；`tiny-llm-java` 则是纯 Java 的教学型小语言模型。这是“用 Java 部署小模型”，不是名为 JAV 的模型。

### 8.3 与本轮 Jev 的区别

`jav`、Javanese、Java JVM、JAV 媒体工具和 `Jev` 是不同检索集合。你给出的链接、近三日开源项目和社区讨论全部指向 `Jev`，所以本轮趋势判断应以 Jev 为主。

## 9. 如果把这股风潮落到 JEV 项目上

若目标是在 `JEV` 项目中研究这种模型范式，最稳妥的项目边界应当是：

1. 先定义一个与供应商无关的 `state + questions -> typed distributions` 协议。
2. 先做离线 benchmark，不把“有概率输出”直接等同于“已校准”。
3. 至少比较 Qwen3-0.6B/NanoJev、Qwen3.5-4B/SemIf、DeBERTa typed-decision 和一个普通 JSON/分类器基线。
4. 评估 accuracy、Brier score、ECE、OOD、端到端 latency、显存和批处理吞吐。
5. 设计高置信度错误、候选项变化、问题改写、状态变长和多语言输入测试。
6. 游戏方向使用预取和缓冲；Agent 方向把执行器验证放在模型输出之后；高风险动作必须有回退。
7. 把“模型复刻”“接口兼容”“应用集成”分别命名，避免把开源兼容服务宣传成 Jev 本体。

不需要先追求一个大而全的聊天模型。这个方向的研究价值在于：一个足够小、足够快、可以量化不确定性、能嵌入控制流的决策部件，如何与规则、搜索、强模型和执行器组成可靠系统。

## 最终判断

本轮风潮的短期热点是 Jev 的“低延迟 typed decision API”，不是一个可以下载的 JAV 小模型。短期最有机会落地的场景是 Agent 路由、浏览器操作、批量分类/评分、内容安全、工作流分流和游戏中的预取式内容生成。中期最值得跟踪的是 NanoJev、SemIf 和 open-jev-deberta 这类开放复刻能否在真实 OOD 任务上保持校准，而不是只在演示中复制概率条。

对这股风潮最准确的技术概括是：

```text
把“会说话的模型”拆成“会判断的模型”和“负责执行的代码”，
再用概率和校准决定什么时候自动化、什么时候升级。
```
