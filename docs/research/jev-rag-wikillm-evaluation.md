# Jev 用于 RAG 与 WikiLLM 类方案的可行性评估

> 评估日期：2026-09-20
>
> 本文是架构可行性讨论，其中“高／中高”不代表当前公开权重已通过文档检索验证。当前软件使用本地 NanoJev、词法召回与原文直出，不调用 Claude 或 TypeSafe API；评测方法与适用限制见 [evals/README.md](../../evals/README.md)。

## 结论摘要

Jev 可以用于构建 RAG，也可以用于 WikiLLM 类知识系统，但两者的定位不同：

| 方案 | Jev 的适合位置 | 可行性判断 |
|---|---|---|
| 传统 RAG | 召回后的重排、证据筛选、冲突检测、注入检测、是否继续检索 | 高；适合作为中间决策层 |
| WikiLLM 类系统 | 知识条目路由、去重、合并/新建判断、冲突检测、来源校验、质量门 | 中高；适合作为控制层 |
| WikiLLM 的全文写作 | 生成页面、摘要、解释、跨文档综合 | 低；需要 Claude/GPT 等生成模型 |
| 向量检索系统 | 生成 embedding、建立向量索引、直接召回全文 | 不适合；需要独立检索组件 |
| 原始 MEMIT WikiLLM | 修改模型权重、把事实注入模型参数 | 不适合替代；两者是不同路线 |

最合理的判断是：

> Jev 不是 RAG 或 WikiLLM 本身，而是一个非常适合放在知识流水线中间的“结构化判断层”。

## 一、这里的 WikiLLM 是什么

“WikiLLM”有两种容易混淆的含义。

### 1. 原始 `laramohan/wikillm`

这个项目的思路是从对话中抽取事实，再使用 MEMIT/EasyEdit 修改 Llama 模型参数，把知识写进模型权重，目标是“不使用 RAG 或外部文档”的持续更新神经知识库。[项目 README](https://github.com/laramohan/wikillm)

Jev 不适合替代这条路线，因为 Jev：

- 不生成开放式文本；
- 不修改模型参数；
- 不负责训练或权重编辑；
- 不承担持久化知识存储。

它最多可以在事实写入之前判断“这个事实是否可信、是否重复、是否与已有事实冲突”，但不能完成 MEMIT 的知识注入。

### 2. Karpathy 风格的 LLM-maintained Wiki

当前更多人说的 WikiLLM，是把原始文档、对话、网页、代码等内容编译成结构化 Markdown Wiki，并通过实体、概念、标签和 `[[wikilink]]` 建立长期可查询知识库。[中文 WikiLLM 项目](https://github.com/wang-junjian/wikillm)的流程包括原始素材摄入、Wiki 编译、问答、Lint、索引和 Obsidian 展示。

这种方案与 Jev 是互补关系：生成模型负责写页面，Jev 负责决定页面应该怎样进入、合并、更新和被查询。

## 二、Jev 用于 RAG 的可行性

### 推荐架构

```text
用户问题
    ↓
查询改写 / 查询分类
    ↓
Embedding + BM25 + 元数据过滤
    ↓
初始召回 Top-K 文档块
    ↓
Jev：逐块判断相关性、可回答性、冲突、提示注入
    ↓
代码按阈值分成证据 / 冲突 / 丢弃
    ↓
Claude / GPT 根据证据生成答案
    ↓
Jev：校验引用、证据支持和是否需要继续检索
```

TypeSafe 的官方 RAG cookbook 正是这种分工：先用 embedding 检索 Top-K，再让 Jev 对每个 passage 进行四个 `Noul` 判断，最后由代码分流，仍然使用 Claude 生成答案。[Classifying RAG passages](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)

官方示例中的四个判断是：

1. passage 是否与查询相关；
2. 是否包含可以直接支撑答案的信息；
3. 是否反驳查询中的事实前提；
4. 是否包含试图控制回答模型的 prompt injection。

代码再按照阈值把 passage 分为：接受的证据、冲突证据或丢弃内容。官方示例明确把证据和冲突分开交给生成模型，而不是让生成模型自行混合处理。

### Jev 在 RAG 中最有价值的部分

#### 1. 语义重排

向量相似度回答的是“文字像不像”，不一定回答“能不能支撑当前问题”。Jev 可以在 Top-K 结果上进一步判断：

- 是否真正回答了问题；
- 是否只有主题相关但缺少关键事实；
- 是否是相似但不适用的文档；
- 是否需要保留多个互相补充的 passage。

#### 2. 冲突分流

普通 RAG 容易把新旧版本、不同配置、互相矛盾的文档一起塞给生成模型。Jev 可以把反驳查询前提或互相冲突的内容单独标记，让生成模型明确说明冲突，而不是把它们拼成一个错误答案。

#### 3. Prompt injection 过滤

知识库中的网页、论坛内容和用户上传文档可能包含针对模型的指令。Jev 可以将“这是证据”与“这是试图控制模型的文本”区分开，再由代码在进入生成 prompt 前排除或隔离。

这只能作为一层检测，不能当作绝对安全边界。生成模型仍应把所有检索内容视为不可信数据，并由代码控制工具权限和副作用。

#### 4. 检索停止和路由

Jev 可以判断：

- 当前证据是否足够回答；
- 是否需要继续搜索；
- 应该查哪个知识库或数据源；
- 是否转向关键词检索、图谱检索或网页检索；
- 哪个模型适合完成最终回答。

这是 RAG 中比较容易被忽略的部分：检索不是一次性取 Top-K，而是一个带有“继续/停止/换路线”判断的循环。

### Jev 不能替代的 RAG 组件

Jev 不应被当作：

- embedding 模型；
- 向量数据库；
- BM25 或全文搜索引擎；
- 文档解析和 OCR 系统；
- 最终答案生成器；
- 引用文本生成器。

官方 cookbook 也体现了这一边界：embedding 负责召回，Jev 负责 passage 分类，Claude 负责写答案。[官方实现说明](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)

### RAG 评估结论

如果目标是“让现有 RAG 少送无关文本、少混入冲突证据、减少 prompt injection”，Jev 很合适。

如果目标是“只用 Jev 构建完整 RAG”，不可行，因为它既不负责召回，也不负责生成自然语言答案。实际方案至少需要：

```text
检索器 + Jev 判定层 + 生成模型
```

## 三、Jev 用于 WikiLLM 的可行性

### Wiki 编译阶段

WikiLLM 类系统通常要把原始资料转成页面、实体、概念和链接。可以设计为：

```text
原始资料
    ↓
解析 / OCR / 代码分段 / 元数据抽取
    ↓
Claude/GPT 生成候选事实、页面草稿和候选链接
    ↓
Jev 判断：
    - 是否为新知识
    - 是否属于已有实体
    - 是否重复
    - 是否与已有事实冲突
    - 是否有充分来源支持
    - 应该合并、更新、建立新页还是标记待审
    ↓
代码写入 Markdown / JSON / 图数据库
    ↓
Git 版本化、索引、反向链接和审查队列
```

### Jev 可以承担的 Wiki 决策

#### 1. 页面路由

给定一条新事实和候选页面列表，Jev 选择它属于哪个实体、概念或主题。候选过多时要先做层级分类，不能一次把整个 Wiki 的所有页面都塞进一个问题。

#### 2. 去重与合并

对“新页面草稿”和“候选旧页面”提问：

- 是否描述同一对象；
- 是否表达同一事实；
- 是否只是措辞不同；
- 是否应合并而非创建新页面。

最终的合并操作必须由代码或生成模型执行，Jev 只给判断。

#### 3. 冲突与版本判断

对新旧事实分别提供来源、时间和版本信息，让 Jev 判断：

- 是否真正矛盾；
- 是否只是不同时间点的有效陈述；
- 新事实是否应该 supersede 旧事实；
- 是否需要保留两者并标注适用范围。

这里尤其要把日期、版本号和数值比较交给确定性代码，不应只依赖 Jev 的自然语言判断。Jev 的类型安全不等于事实推理绝对正确。

#### 4. 来源和引用质量门

Jev 可以判断页面中的断言是否有对应来源、来源是否支持该断言、证据是否直接，进而把条目分为已确认、待复核和证据不足。

#### 5. Wiki 查询路由

用户提问时，Jev 可以判断应该：

- 直接查某个概念页；
- 沿实体关系继续走图；
- 搜索原始来源；
- 查历史版本；
- 调用生成模型做跨页综合。

## 四、Jev 不能独立构成 WikiLLM

WikiLLM 的核心价值在于“知识被持久化、组织、交叉链接和版本化”。Jev 本身没有：

- Markdown 页面存储；
- Wikilink 图；
- 原始资料归档；
- Git 版本历史；
- 页面内容生成能力；
- 长期知识的自动维护机制。

因此不能做成：

```text
原始文档 → Jev → 完整 Wiki
```

更合理的是：

```text
原始文档 → 生成模型编译候选 Wiki
                  ↓
                 Jev
         做选择、校验、路由和冲突判断
                  ↓
          代码写入持久化知识库
```

生成模型做“写”，Jev 做“判”，代码做“存、验和执行”。

## 五、推荐的组合架构

### 最小可用版本

适合先验证价值：

1. 本地保存 `raw/` 原始资料；
2. 使用 Claude/GPT 把资料转成带来源的 Markdown 页面；
3. 为每页生成标题、实体、概念和来源元数据；
4. 用 embedding/BM25 建索引；
5. 查询时先召回 20 个候选页面或 passage；
6. Jev 对候选进行相关性、证据性、冲突和注入判断；
7. 代码保留证据和冲突两个区块；
8. Claude/GPT 依据证据生成带引用的回答；
9. Jev 再对回答中的断言做引用支持检查；
10. 只有通过规则的内容才写回 Wiki。

### 生产化版本

应增加：

- 原始资料不可变保存；
- 每条断言绑定来源、时间、版本和哈希；
- 事实级而非仅页面级的证据索引；
- 新旧事实的 supersede/contradict 关系；
- Git 或数据库事务写入；
- 人工审核队列；
- Jev 低置信度时的回退策略；
- 召回、Jev 判定、生成、引用校验的离线评测集；
- 对每个阈值分别测 precision、recall 和人工审核率。

## 六、关键风险

### 1. Jev 只能在提供给它的候选中做判断

如果初始向量检索漏掉了真正相关的文档，Jev 无法凭空召回它。它可以重排候选，但不能修复召回系统的全部问题。

### 2. 低概率不等于不相关

阈值是业务策略，不是模型事实。对于法律、医疗、金融、版本迁移等场景，应该保留“未知/待审”分支，不能简单地把低分内容永久丢弃。

### 3. 每个候选可能需要一次 Jev 判断

官方 RAG cookbook 的示例对每个 passage 发一次请求，再限制并发；因此最终成本和延迟与 Top-K 直接相关。要通过候选去重、粗筛、批量策略、缓存和分层路由控制成本。

### 4. 置信度不是安全证明

Jev 返回的是结构化概率和置信度，方便代码设阈值，但仍可能做错判断。高风险写入应要求来源证据、确定性校验和人工确认。

### 5. 数据可能外发

Jev 是托管 API，不是默认本地模型。RAG passage、Wiki 草稿、用户问题和元数据可能发送到 TypeSafe 服务。敏感知识库必须先核对数据保留、训练使用、地域、企业协议和脱敏要求。

## 七、最终建议

### 如果优先做 RAG

建议立即验证“Jev 作为 reranker + evidence gate”的方案。它是 Jev 最直接、公开文档支持最明确的用法。先用 100 到 300 个真实问题建立评测集，对比：

- 仅向量 Top-K；
- 向量 + 传统 reranker；
- 向量 + Jev；
- 向量 + Jev + 生成模型引用校验。

关注的不只是最终回答相似度，还要测证据召回、冲突识别、注入过滤、引用准确率和总成本。

### 如果优先做 WikiLLM

建议先把 Jev 放在“知识入库控制层”，不要让它负责页面写作：

```text
生成模型：抽取事实、写页面、写摘要、生成链接候选
Jev：去重、路由、冲突、证据、更新策略
代码：持久化、版本、索引、权限、事务和审计
```

### 总体评级

```text
RAG 后置重排/证据过滤       8/10
RAG 查询路由/停止判断        8/10
Wiki 条目去重/冲突判断       7/10
Wiki 图谱导航                6/10
Wiki 页面生成                2/10
向量检索/embedding           1/10
替代 MEMIT 式知识编辑        1/10
```

最后的判断是：

> Jev 很适合成为 RAG 和 WikiLLM 的“判断内核”，但不能成为它们的“知识载体”或“语言生成器”。最有价值的落点是减少无效上下文、筛选证据、识别冲突、控制知识写入和决定下一步检索；最终内容仍应由生成模型产生，知识仍应由可追溯的文件、数据库或图谱保存。
